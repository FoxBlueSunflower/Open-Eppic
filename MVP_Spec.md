# Open Eppic — MVP Specification (v1.4)

The Covenant (`Open_Eppic_Covenant.md`) is the highest overarching philosophy of this build. Every feature, workflow, architecture, and process decision in this document is subordinate to it and must be assessed against it.

---

## Glossary

- **Space** — a walled, multi-tenant community hub; the unit of hosting/billing.
- **Category** — broadest structural bucket (e.g., Fiction / Non-Fiction); broad enough that natural borders exist between them; edge cases acknowledged.
- **Brand** — an IP identity within exactly one Category; owned by one creator.
- **Element** — the universal content entity. Types: Work, Chapter, Character, Setting, System, Event, Item, Block.
- **Work** — an Element representing a finished expression (book, illustration, etc.); the target of Collection publishing and the trigger of the activation gate.
- **Block** — a reusable content chunk; in MVP, static copies only.
- **Derivative** — an Element copied from an original, permanently stamped with `derived_from_id`; non-monetizable, non-derivable, Space-locked.
- **Activation gate ("Home Work" rule)** — original Elements cannot be linked to or derived from until their creator links them to a published Work (establishes legal "expression" and acts as a quality gate).
- **Collection** — a user's gathering of Elements: flat/filterable first, then ordered/hierarchical; publishable to a Work.
- **Endorsement tag** — a tag applicable only by the original creator of an Element to derived/linked Elements; requires an owner-authenticated write path (deferred, high priority).
- **Covenant** — `Open_Eppic_Covenant.md`; the governing philosophy of the entire build.
- **Transparency Log** — the Covenant's public accountability record (Commitment 6, Part IV Transparency). Split by kind per Locked Decision 16: constitutional interpretations as GitHub markdown; moderation outcomes as public data plus a baseline periodic markdown report. Opens with a pointer to **Open-Eppic-Research-and-Theory** for pre-existing history. Report cadence: monthly (automated). Constitutional-interpretation log takes the broad reading — see `transparency/README.md`.
- **Grant** — a licence formed directly between two members when one accepts another's standing offer (activation → derivation). Recorded, timestamped, and version-stamped by the platform, which is never a party to it.
- **Additional Permission Layer** — an additive permission a rights-holder grants on top of the base derivation licence (e.g. commercial/bounty use, or off-platform use). Never subtractive; always separately consented.
- **Qualifying Instance** — any publicly accessible instance of the published software that preserves lineage records, enforces the licence terms, and provides member exit/portability. The venue in which grants remain valid; no body certifies this.
- **Registrar** — the platform's role with respect to rights: it records, timestamps, version-stamps, and evidences grants, and holds no rights in members' work. Precisely, a **records custodian operating a system of record** — never a notary. A notary public is a natural person holding a state commission; a company cannot hold one, and holding itself out as a notary is a criminal offence in most jurisdictions. "Notary" was used as internal shorthand in earlier drafting and is corrected wherever it could become member-facing (2026-08-11); the architecture is unaffected.

## Build Methodology

- **Walking skeleton first**: one end-to-end vertical slice (create Space → Brand → Element → link → derive) before building features wide.
- **Before building**: define user "loop" pathways and journeys for each user type (Space Owner, Creator, Reader); assess and design MVP UI with deferred features in mind so layouts don't foreclose them.
- **RLS-first security**: design and assess Row-Level Security policies before UI. Treat every table as public-by-accident until proven otherwise; test with a second dummy account from day one.
- **Server-side authority**: ownership (`owner_id`), lineage (`derived_from_id`), endorsement writes, and activation-gate flips are set by Postgres triggers / Supabase Edge Functions — never by client submissions from WeWeb.
- **Soft deletes only**: `deleted_at` timestamps + tombstoning. Hard deletes are forbidden — lineage must survive deletions, and DMCA takedowns must hide content while preserving lineage records.
- **Schema under version control**: all schema changes via Supabase CLI migrations committed to GitHub (never dashboard-only edits). This is both engineering hygiene and the Covenant's forkability/transparency commitment. The official public GitHub repo is the "Home of transparency."
- **Seed data script**: built alongside development — populates a demo Space with a full graph (brands, elements, links, a derivative, a collection) for testing and demos.
- **Editor "feel" standard**: zero cursor/typing lag is the bar. Prefer a slim editor over a feature-rich one that lags. The editor gets its own clean, dedicated page to maximize its performance budget.
- **No bulk or assisted import in the MVP; editor primacy (2026-08-11).** A robust, user-friendly creation and editing system is the primary build target — it is the heart of the system, and import tooling is not a substitute for it. Consequence accepted: manual entry of a completed canon becomes a **first-run experience** problem the editor and onboarding must absorb, which makes the first-run screen the highest-stakes surface in the launch-core set. (Note: founder-concierge onboarding for the first cohort is adopted, time-boxed, and explicitly not the durable mechanism — see Roadmap 2026-08-07; community capacity, not founder labor, is the durable answer, per Commitment 12 and Part IV No Siloing.)
- **Per-type metadata contract**: define a minimal documented JSON shape per Element type before building (prevents inconsistent polymorphic JSONB sprawl). To be worked out together; YAML/JSON format appropriate here.
- **High-level phase design** includes user interviews (per *Deploy Empathy*; user has sources) and pre-launch legal review — IP attorney on license text + DMCA agent registration with the US Copyright Office.
- **Substrate/covenant-layer separation (design discipline, not a build target)**: keep Open-Eppic-specific policy out of core schema where doing so is cheap, so the element-graph substrate stays vertical-agnostic. This is posture only — **do not build "the general system."** Building a generic substrate ahead of a working Open Eppic would strain the Aim's constancy and Human Scale. The general case emerges from a well-built specific case; it does not precede it.
- **Namespaced metadata extension points**: the per-type metadata JSON contracts each reserve a namespaced extension slot, so a Space can later attach its own schema extensions without touching core types. Cheap now; the whole cost of not foreclosing Space-level metadata self-governance.

## Locked MVP Decisions

*Do not reopen unless the user asks. If a request conflicts with one of these, flag the conflict rather than silently complying.*

1. **Spaces are walled gardens for linking/derivation** — no cross-space links or derivations. However, a user **can transfer or copy their 100% original content between Spaces**. Derivative content is permanently locked to its Space.
2. **Space membership**: Readers enter and exit Spaces freely; creators join by invitation/approval from the Space owner (with original IP owners deciding on their own Elements). Formal invite mechanics deferred. **Rationale and accepted strain (2026-07-21):** the creator gate is deliberate Deming — quality is built in upstream, and managing who enters is managing quality at the source. This **knowingly strains** Commitment 9 (a relational gate filters hardest against the creator with no network), Commitment 12, and Part IV Hospitality / the "stranger unwelcomed" shape in Part III. Accepted for now on a promise of remedy: the intended improvement is an **objective educational formation gate** (free, published criteria, covering how the platform works — especially legally) that replaces "who you know" with "what you have learned," discharging Part VII's onboarding-as-covenant-formation item. Mitigations meanwhile: readers are ungated, the gate is per-Space not platform-wide, and a creator may host their own Space. Logged as its own entry **when the formation gate is decided**, not before. **Amended 2026-08-11:** the "formal invite mechanics deferred" clause is lifted in part — an **in-platform invitation surface enters the MVP**: owner-initiated invite plus **member-initiated request-access**, the latter being the load-bearing half of the Commitment 9 repair, since off-platform-only invitation leaves the un-networked creator no visible path in. Request-access is membership, not enforcement, and writes nothing to the moderation-outcomes schema; requester identity is visible to the Space owner only (a scoped, consent-based exception to the otherwise-private identity posture). Formation weight is **graduated by role**, not uniform: minimal for readers at first entry, greatest at the **becoming-a-creator** threshold, and deliberately light at point-of-creation (a reminder, not a formative wall). This answers the formation-gate question "does it gate any creation or just derivation" — the weight lands at becoming a creator. The deferred formation course itself is unchanged and still owns the deep answer. See transparency log 2026-08-11-community-mechanics.
3. **Single ownership only** for Spaces, Brands, and Elements. Multi-ownership deferred.
4. **Brand belongs to exactly one Category.** Categories are broad with natural borders (e.g., Fiction / Non-Fiction). Tags handle all granularity (genre, warnings, discoverability).
5. **Polymorphic Element graph**: all entity types (Work, Chapter, Character, Setting, System, Event, Item, Block) live in one `elements` table with a `type` column; connections via a central `element_links` join table (adjacency list).
6. **Permanent lineage**: `derived_from_id` set once at derivation, immutable thereafter. Derivatives are non-monetizable and non-derivable. Derivation as a *sanctioned, lineage-tracked mechanic* exists only on the platform — a platform-scope claim, not a claim that people can't post crossovers elsewhere.
7. **Home Work activation gate**: original Elements are locked from linking/derivation by others until their creator links them to a published Work. **Activation is the creator's consent moment for derivation (2026-07-22).** Activating an Element opens it to derivation by the members of its Space, and that opening is not selectively withheld — there is no read-only publishing state, now or planned. Creator control is exercised at three points: whether to bring a work here, which Space to place it in, and whether to activate. Withdrawal is prospective-only (no new derivations; Works already made stand). This is stated to creators before they activate anything (Commitment 6). See Covenant v0.4, Commitment 3, "What stewardship controls here," and transparency log 2026-07-22.
8. **Editor**: JSON block-based output stored as JSONB; no HTML WYSIWYG. **Specific editor library is an open strategic decision** — TipTap has commercial licensing costs conflicting with lean financials; evaluate alternatives (Editor.js, ProseMirror direct, Lexical, others) on cost, WeWeb custom-component compatibility, JSON output structure, and typing-lag performance.
9. **Blocks in MVP: static copies only.** No live-sync or review pipeline.
10. **Element versioning (minimal) is in the MVP**: content updates are append-only — saving publishes a new immutable row in an `element_versions` table rather than overwriting, with a current-version pointer on the Element. This is what Publish-to-Work re-publishing hangs on, guarantees derivatives/static Block copies never break, and lays the substrate for the deferred diff/review pipeline. It must exist to test and resolve soft-delete workflows and related interactions. **No versioning UI in the MVP** (no history browsing, no restore) — unless a minimal UI proves necessary to test how core functions interact with versioning. What stays deferred: live-sync, frozen-state management, side-by-side diff review, and version-change notifications beyond the basic "a Work you follow was updated."
11. **Collections are in the MVP** as part of the higher-level CRUD flow: "Collect" button on any Element → flat, filterable gathering (built first), then ordered/hierarchical structuring, then **Publish to Work** (the only publish target). Priority order: the editor and Element/Block CRUD loop come first and must feel streamlined before Collection work.
12. **Following is in the MVP** (follow Users, Collections, Elements). **Amended 2026-08-11:** Following is no longer the *sole* Reader mechanic — **Element-anchored discussion enters the MVP, sequenced into Phase 4 alongside the governance baseline and never before it.** Scope: discussion anchored to an Element or Work, scoped to Space membership, readers included. **Not** a feed, not global, not ranked, no karma, no likes. The Commitment 11 assessment the Deferred list required is hereby made, not assumed: work-anchored talk complies because the artifact holds the floor rather than the speaker, and it is Space-bounded with no cross-Space amplification (Commitment 11, Commitment 12, Part IV Hospitality, Human Scale). Discussion contents are visible to Space members only; anonymous visitors see a count. Three conditions bind it: **norm salience at the point of creation** (light draft-time contextual guidance — Phase 2, and cheap regardless of discussion); **victim-side workflow is a Phase 4 requirement, not a Phase 4 question**, since discussion is where interpersonal harm happens and the capture schema records nothing of the reporter's own resolution; and **the appeals procedure is defined before first use** (Covenant Part V is still a placeholder). Named strain accepted: the formation gate is Deferred, so the discussion surface arrives ahead of the upstream formation mechanism the Deming frame depends on — compensated by norm salience, endorsement (LD 20), small Spaces, and the LD 2 invite/request-access gate. Because Phase 4 is pre-launch, this costs no MVP scope ahead of the editor and Element loop. See transparency log 2026-08-11-community-mechanics.
13. **Rights architecture: direct peer grant, platform as registrar, base licence plus additive permission layers (DECIDED 2026-07-22; text still attorney-gated).** Activation constitutes a standing offer of the Open Eppic Derivation License to a Space's members; each derivation is acceptance, forming a licence **directly between original creator and derivative creator**. The platform records, timestamps, and version-stamps grants and **holds no rights in members' work** — registrar, never rights-holder. Layer 0 (MVP): on-platform, non-commercial, non-exclusive, venue-restricted, no sub-derivation, lineage-stamped attribution, **irrevocable as to derivative Works already made**, withdrawal prospective-only; the derivative creator's own original contributions remain theirs absolutely (17 U.S.C. §103(b)) and this clause leads the text. Layers 1 (commercial/bounty) and 2 (external/off-platform, person-to-person, platform as **records custodian never a party**) are additional permissions granted by the rights-holder; **the base licence carries the additive-permissions hook from the outset** so later layers need no re-consent. Which permissions a Space offers is set at Space level within a Covenant floor, and a Space's active permissions must be disclosed to any member bringing content in. Hub-and-spoke (platform-held sublicensable rights) is **rejected permanently as violating Commitments 3 and 5** — the CLA pattern in content form. **Attorney review of the final license text remains a Phase 5 launch gate: drafts (including AI-assisted drafts) are requirements work, non-final by definition (2026-07-17; Commitment 3).** Reference: `docs/rights-and-legal-architecture.md`; transparency log 2026-07-22.
14. **Governance baseline**: report button on every Element + formalized DMCA takedown flow + platform-owned Public Domain administrative account (user submissions via review queue).
15. **WeWeb usage**: native/premade WeWeb elements wherever possible; custom coded Vue components only where truly necessary (e.g., the JSON block editor).
16. **Transparency log is split by kind: interpretations as markdown, outcomes as data — infrastructure precedes decisions.** Constitutional interpretations (rare, high-weight applications of the "When Commitments Appear to Conflict" rules) are written as markdown and committed to the public GitHub repo — git history is the audit trail. Moderation outcomes (frequent, structured — DMCA actions, enforcement decisions, pattern-level statistics) are stored as data with a public read path. The reporting floor is **data plus a simple periodic markdown report** of aggregated hard numbers (totals for the period; no comparisons, no charts) — both required at minimum, not data alone. Comparative reporting and visualization are later enhancements. This log infrastructure must exist **before** it is first exercised. **Amended 2026-07-17:** in Phase 0 this means the markdown convention (done) plus a committed **capture-schema specification** for moderation outcomes; the physical table, public read view, and report generation are built in Phase 1's initial schema pass from that spec — before the platform can produce its first moderation datum, preserving the infrastructure-precedes-use principle (see transparency log, 2026-07-17 rescope entry). The markdown log opens with a historical-note pointer to the pre-existing **Open-Eppic-Research-and-Theory** repo, where prior decisions and research already live — this log is not a re-capture of that history, only what follows it. Detailed shape (table schema, public view/RLS design, report cadence) is an Open Strategic Decision, resolved in Phase 0.
17. **Repo license & contributor terms: AGPL-3.0-or-later + DCO; CLAs refused permanently.** AGPL-3.0-or-later chosen for immediate forkability (Covenant Part VI; Commitments 4, 6) and anti-extraction copyleft (the Aim). "Or-later" (AGPL §14's own option) provides covenant-safe license-version migration without creating platform-held relicensing rights. Contributions require DCO sign-off (provenance certification only). CLAs and copyright assignment are rejected as extractive (Commitments 3, 5) — permanently, not deferred. Custom unreachable-contributor clause: referred to IP attorney; adopted only if draft language survives Covenant assessment, as its own transparency-log entry. Accepted consequence: relicensing outside the AGPL family requires per-contributor consent — the platform binds itself alongside its contributors. See transparency log entries of 2026-07-16.
18. **Contribution policy: constrained scope, quality-first core, open periphery.** Core contributions are accepted only when aligned with communicated build goals and focus areas. Security contributions are welcome at all times, as are bug reports and reproduction cases, documentation and onboarding writing, accessibility review, user-research participation, design/UX critique, and covenant scholarship. Core development prioritizes systemic quality (Deming) over feature accretion; contributor feature energy is directed toward add-ons and integrations. Every accepted contribution is recorded in the public contribution ledger (`transparency/contribution-ledger.md`) — chosen public name only, no contact information (Commitment 1 / conflict rule 3).
19. **Forkability is four strata; launch age floor is 18+.** (a) **Code** forks automatically (AGPL-3.0-or-later, LD 17). (b) **Content** does not auto-replicate: a fork begins empty, creators consciously port their **originals** (derivatives are Space-locked, LD 1/6), and the venue definition keeps peer grants valid at a destination the creator chose. Venue is **objective and self-executing** — any publicly accessible instance that preserves lineage records, enforces the licence terms, and provides member exit qualifies, plus an objective cessation/insolvency trigger; **no body certifies legitimacy**, because any such body becomes the thing worth capturing. (c) **Identity does not fork**: forks operate under a **new name**; the mark is defensively registered (founder-filable, like the DMCA agent) and bound by a published **non-weaponization policy** permitting nominative fair use. (d) **Personal data does not fork**: member **self-serve export** only; `private_notes` is never exported to successors. **Launch is 18+**, foreclosing COPPA and contract-capacity risk; revisiting 13+ is its own future decision. Accepted consequence: derivative durability is Space-scoped, disclosed to derivative creators at derivation. See `docs/rights-and-legal-architecture.md`; transparency log 2026-07-22.
20. **Endorsement tags are in the MVP.** Moved out of Deferred Features 2026-08-11. An endorsement tag is applicable only by the original creator of an Element, to derived or linked Elements. Rationale: it gives the world owner a stewardship lever that is *not* the LD 2 invite gate — without it, all world-owner control concentrates in who enters the Space, at exactly the moment the Commitment 9 strain is highest (launch). Covenant: strain-reducing — Commitment 9 (the invite gate carries less weight), Commitment 7 (recognition rather than exclusion as the primary steward tool), Commitment 3 (stewardship exercised without a per-derivation veto, consistent with LD 7 and the 2026-07-22 participation-is-constitutive amendment). Architecture: requires the owner-authenticated write path already named in this spec; endorsement writes are set server-side by trigger or Edge Function, **never** client-submitted from WeWeb. **Open design question:** whether absence-of-endorsement is a visible state at all, and whether "not endorsed" is distinguishable from "not yet endorsed" — a Commitment 1 / Commitment 7 dignity question, undecided, and formational when it is decided.
21. **Visibility affords participation; the creator threshold is Organize.** (a) An Element is in exactly one of two states — **creator-only** (pre-activation or draft) or **visible** (post-activation). There is no visible-but-inert state: every visible Element is **at minimum Collectable**. This is a standing invariant — no future feature may show an Element publicly while affording neither Collect nor Derive. It does not conflict with LD 6: a derivative is visible and Collectable while remaining closed to further derivation, which is why derivability is a *computed* fact and not a stored flag. (b) The reader→creator path is **Collect / Organize / Derive**, and the creator line is crossed at **organizing**, not at collecting or publishing. *Collect* (reader, ungated) gathers any visible Element or Block into an unordered Collection. *Organize* (creator, gated) imposes order or hierarchy — the authorial act, behind the formation gate. *Derive* (creator, gated) creates a lineage-stamped child. Publish-to-Work follows an organized Collection; the threshold is the organizing, not the publish click. This maps onto LD 11 exactly — the build sequence *is* the reader→creator progression, and the gate is the flat→ordered boundary. (c) Ratified visibility posture: **follower identity is never exposed to anyone, including the followed** — only an aggregate count is (consistent with the moderation schema's refusal of correlatable per-member tokens on Commitment 1 grounds); Collections are publicly viewable while organize/edit is gated per (b); pre-activation Elements and draft Works are creator-only; `private_notes` is hidden from every role but the acting moderator, enforced at the RLS/view layer per moderation-schema invariant 2. **Carried open:** a Work published from a Collection of *collected* Elements raises a selection-and-arrangement question against the retained owners of those Elements — an open rights-architecture item touching LD 6/13, attorney-gate-adjacent, arising only at Publish, which is creator-gated. See `docs/journeys/screen-inventory-and-visibility-matrix.md`; transparency log 2026-08-11-participation-surface.

## Open Strategic Decisions

- **Editor library** — cost, WeWeb custom-component compatibility, JSON output structure, typing-lag performance.
- **Perpetual license form — architecture DECIDED 2026-07-22** (see Locked Decision 13 and `docs/rights-and-legal-architecture.md`). Remaining open: the final licence **text**, gated on IP-attorney review at Phase 5, plus the attorney checklist items — consideration structure, choice-of-law and non-US moral-rights posture, clickwrap sufficiency, trademark policy language, and the Layer 2 external-grant template when those layers are built.
- **Contributor recompense — covenantal, not transactional.** Recompense begins with being heard, worked with openly, and publicly recognized; extends to participation in future value systems (monetary or otherwise) if/when they exist, decided transparently and logged at a named milestone. Symmetric constraint: no provision may enable contributors to extract from the platform or its members. Future brainstorm scoped, deferred with monetization: reach/exposure micro-compensation; member advertising limited to on-platform Brands/Works/Elements (the platform itself does not advertise — advertising would introduce transactional strangers into the covenant community); gift-economy structural alignment. Each requires assessment against Commitments 9 (rich-get-richer gradients drown smaller voices) and 11 (reach rewards can quietly become an engagement economy) before design. **Pricing constraint (permanent, Covenant-derived, 2026-07-22): open source, metered service.** All code is published (LD 17); paid tiers may consist only of hosting, capacity, operations, support, facilitation, and infrastructure-cost-driven metering — **never** withheld source, **never** a deliberately degraded free tier, and **never** tier-gating of being-heard, appeals, equal process, exit, or portability (Commitments 4, 6, 9; Part IV Transparency). Feature-based open core and dual licensing are foreclosed, the latter structurally (it would require the CLA permanently refused in LD 17). **Framing correction (2026-07-22):** economic survival is *upstream* of Commitment 9, not opposed to it — a platform that dies serves no one, and Commitment 9 guarantees the smaller voice is heard, defended, and given equal process, not free unlimited service. **Open edge:** who funds the anchorless newcomer who wants their *own* Space (Spaces are the unit of hosting/billing). **Commitment 9 flag:** any control-for-pay gradient must be tested before design — control granularity, not price, is the lever, or only large IP owners can afford to protect a world.
- **Rights-infrastructure-for-organizations — untested strategic hypothesis.** The thesis that the durable asset is consent-scoped provenance (who may do what with whose work) sold into verticals where that question is currently manual and lawyer-shaped — technical documentation, legal boilerplate, franchise licensing, curriculum reuse, AI-training provenance — with the lightweight-CCMS case as the probe. **No customer has been asked to pay for anything; external provenance-market signal is adjacent (file-authenticity) rather than identical (derivation-lineage-plus-consent).** Discipline: **test the hypothesis cheaply, do not build the product.** TTRPG remains the beachhead. Held in founder working drafts; not committed until decided.
- **Register-and-attestation model — untested effectuation probe (opened 2026-08-11).** A sharper, narrower possible first shape: Open Eppic as a public register of third-party creative licensing rather than a hosting platform. A rights-holder brings **their own** licence (OGL, ORC, a publisher's own third-party licence, or the Open Eppic Grant as default template) and lists which of their Elements are open; a participant registers a dated, hash-anchored **attestation** of what they relied on, which exact licence version governed it, and what in their own work is independently theirs. The instrument is drafted at `docs/attestation-draft-v0.1.md` (**`draft — not decided`**). What it would supply that no existing instrument does: per-element rather than blanket opening, an **identified counterparty** (OGL and ORC are anonymous and worldwide by construction), version-plus-content-hash evidence of what text was relied on (the OGL 1.1 failure), and computed upstream attribution chains (ORC §III.b.i requires attributing all upstream licensors; OGL requires reproducing every prior notice verbatim). **Discipline: test the hypothesis cheaply, do not build the product** — the cheap test is rights-holder conversations, not a build. Distinct from the rights-infrastructure-for-organizations hypothesis above: that one is a B2B vertical thesis, this is a consumer-facing register. **Adopting this shape would amend LD 13** (from "activation is a standing offer of the Open Eppic Derivation Licence" to "the register records whatever licence the rights-holder brings, with the Open Eppic Grant as default template") and is therefore formational — transparency-log entry **when decided**, not before. Nothing is decided. Carried open alongside it: (a) whether register listings are Elements or a separate index record type — if Elements, **LD 21a needs a third state, *listed* (visible, Collectable, not derivable), between *creator-only* and *activated***, which is conforming but is a Locked-Decision amendment and moves `is_derivable` from computed to stored; (b) an **external Work type** for works the platform does not host (an Amazon ebook, a convention print run, a publisher's own catalogue), needed so a licensor can satisfy LD 7's Home Work gate without moving their catalogue here; (c) a **provenance-dispute flow** distinct from content moderation and from DMCA — "that element isn't yours" is not "that content is harmful"; (d) **identity verification** required for the attesting act only, reading and collecting ungated — a named Commitment 9 gradient, since verification falls hardest on those without documents or whose legal name differs from their public one; (e) counter-acknowledgment absence as a visible state, the LD 20 dignity question on a second surface.
- **Definition of "Evil" in the Covenant (Commitment 2)** — needs fleshing out; gates Content Guidelines and moderation design.
- **Transparency log detailed shape** — capture schema **DECIDED 2026-07-17**: committed as `transparency/moderation-outcomes-schema.md` v1.0 (nine fields, fillable reasoning templates, four invariants; pseudonymous per-member tokens excluded — reasoning stated in the spec's invariant 3). Remaining: table DDL, public view/RLS design, and report generation implemented in Phase 1 from that spec. Cadence decided: monthly, automated.

## Deferred Features

*Design around these — MVP architecture must not foreclose them — but do not build.*

- **Seasonal events / jams** — dated, finite, chosen, with rest between: the growth mechanic that is not virality. Complies with Commitment 11 (rhythm is not manufactured urgency) and Human Scale. Deferred by founder decision 2026-08-11; recorded so it is not lost.
- **Versioning UI** — history browsing, restore, diffs (storage substrate is in MVP; see Locked Decision 10).
- Formal invite mechanics for Spaces.
- Cross-space linking/derivation; Open Eppic crossover Space mechanics (original Brands and Elements only when built).
- Block live-sync, frozen states, diff review pipeline, notifications engine.
- Multi-ownership; IP/Brand transfer.
- **Additional Permission Layer 1** — commercial/bounty permissions lifting the base licence's non-commercial restriction; menu set at Space level within the Covenant floor (LD 13).
- **Additional Permission Layer 2** — external/off-platform permissions (convention art, physical goods, fan works); always person-to-person and bespoke, with the platform as **records custodian, never a party** (LD 13).
- **Cross-Space derivative migration** — derivatives are currently Space-locked (LD 1/6). A future solution is a **re-grant with preserved lineage**, not a relocation: it needs the original creator's consent, compatible Space permissions at the destination, resolvable lineage, and grant-record continuity.
- **Space-level metadata extensions and Space profiles** — a Space attaching its own validated schema extensions and configuring which Element types it surfaces (the lightweight-CCMS use case). Global types stay global; **fully Space-defined Element types are rejected** (fragments the commons and breaks LD 1 transfer, makes aggregate moderation reporting incoherent, invites JSONB sprawl). The Phase 0 namespaced extension points are what keep this open.
- **Offline local-first editor/viewer** — a user-held editor/viewer for Elements and Works, independent of any instance (a fifth, user-held expression of Commitment 4). Proposed design: **export/import round-trip with server-authoritative identity — never bidirectional sync**; the server re-derives ownership, lineage, versions, and grants on import and ignores all client claims. Needs its own ADR before any build; interacts with the open editor-library decision (a clean markdown↔JSON mapping is a selection criterion).
- Monetization, marketplace, licensing agreements beyond the core perpetual license, payment splits.
- **Bounty system** — Readers place bounties on content they want; creators fill them (big; may or may not make it).
- **Services offering system** — creators offer services within IP + agreements with original IP owners (big; may or may not make it).
