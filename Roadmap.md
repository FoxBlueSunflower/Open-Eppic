# Open Eppic — Build Roadmap (v1.3)
 
The Covenant (`Open_Eppic_Covenant.md`) is the highest overarching philosophy of this build. This Roadmap is subordinate to it and to `MVP_Spec.md`, and must be assessed against both. Unlike the Covenant, this is a **living document** — phases get checked off or annotated as work proceeds, and scope shifts are recorded here rather than left to drift silently. This Roadmap does not override MVP_Spec.md's Locked Decisions; if a phase turns out to require reopening one, that conflict is flagged the same way any other locked-decision conflict is flagged.

## Phase 1 — Walking Skeleton
 
- One vertical slice: create Space → Brand → Element → link → derive, end-to-end, ugly UI, real RLS.
- RLS policies designed and tested with a second dummy account before any UI work, per methodology.
- Supabase schema as versioned CLI migrations from commit #1 — no dashboard edits. If the transparency-log data table (Phase 0) isn't already migrated in, it belongs in this initial schema pass.
- Seed data script alongside this, not after.
## Phase 2 — Core CRUD Loop
 
- Editor (once library is chosen) gets its dedicated page; typing-lag is the gate for shipping it.
- **Norm salience at the point of creation**: light contextual guidance in the editor/publish flow at draft time. Proactive guidance teaches; reactive explanation does not, and Deming's build-quality-in-upstream says this is the actual moderation system while the report button is the exception handler. Commitment 11 boundary: contextual guidance complies; nagging, repeated interruption, or gates beyond what the Covenant requires do not. Cheap, and warranted independent of the Phase 4 discussion surface.
- Element/Block CRUD, per-type metadata forms driven by the JSON contracts from Phase 0.
- Activation gate (Home Work rule) enforced server-side (trigger/Edge Function).
- Element versioning substrate (append-only `element_versions`, current-version pointer) — no UI yet.
- Soft-delete/tombstone pattern implemented and tested against lineage-survival requirement.
## Phase 3 — Collections & Publishing
 
- Collect button → flat/filterable Collection → ordered/hierarchical → Publish to Work.
- This is explicitly sequenced *after* the editor/Element loop is streamlined, per Locked Decision 11.
## Phase 4 — Reader Loop & Governance Baseline
 
- Following (Users, Collections, Elements).
- **Element-anchored discussion surface** (LD 12 as amended 2026-08-11): anchored to an Element or Work, Space-scoped, readers included; no feed, no ranking, no karma or likes. Ships **alongside** the governance baseline in this phase, never ahead of it.
- **Victim-side workflow** — a requirement of this phase, not an open question of it. The capture schema records `report_received`, `no_action`, and the appeal outcomes, but nothing records that the reporter was told how their report resolved. Whether that needs a field or only a workflow step is what the mini-spec decides.
- **Appeals procedure defined before first use** — Covenant Part V is still a placeholder, and the first moderation action must not be the thing that improvises it.
- Report button on every Element, DMCA takedown flow, Public Domain admin account with review queue.
- **Wire these governance features into the transparency log already built in Phase 0** — every DMCA action, moderation decision, and Public-Domain-account intervention writes a log entry as part of the workflow, not as a follow-up step. This phase does not stand up the log itself; that infrastructure already exists by this point.
- These features are Covenant-load-bearing (Commitments 1, 6, 9) as much as feature work — not a "nice to have" tacked on later.

## Open Tensions to Watch
 
- **Discussion posts are not representable in the capture schema (accepted 2026-08-11, deliberately unresolved).** `transparency/moderation-outcomes-schema.md` v1.0 defines `element_type` as a nullable enum matching LD 5's Element types, and names it the primary pattern dimension of the monthly report; a discussion post is neither an Element nor an account-level action, so moderation of discussion would aggregate as null — indistinguishable from account restrictions and removals. Since the spec forbids recording any moderation datum outside the schema, there is no workflow-layer workaround. This **strains Commitment 6** (a monthly report that structurally cannot surface a whole class of enforcement is not the truth about the system) and **strains Commitment 9** (the pattern is unauditable for precisely the harm smaller members are most exposed to). It becomes a violation only if Phase 4 ships discussion against an unamended schema. A remedy was assessed and held for future work: a nullable `subject_type` field (`element` | `discussion_post` | `account`), additive and permitted by the schema's own amendment rule, with `element_type` populated only when `subject_type = element`. **Founder decision 2026-08-11: deferred to the Phase 4 mini-spec.** Consequence knowingly accepted: Phase 1's initial schema pass builds the table from v1.0 and will require a migration for a requirement already known today. The amendment must land before Phase 4 ships discussion.
- **Provenance disputes are not content moderation, and no flow exists for them (opened 2026-08-11).** "That element isn't yours" is a different act from "that content is harmful," and the Phase 4 governance baseline currently contemplates only the latter plus DMCA. The DMCA half is covered — the designated agent is registered (2026-07-18) and `dmca_takedown` / `dmca_counter` / `dmca_restore` are in the capture schema. The **non-DMCA half is not**: a rights-holder objecting to an originality claim without filing a formal notice has no path, and the objection is about attribution and provenance rather than content. This is latent today and becomes load-bearing under the register/attestation probe (MVP_Spec Open Strategic Decisions), where the platform publishes originality claims it does not verify. Not a strain yet — no such claims are published. Scope into the Phase 4 mini-spec alongside the victim-side workflow; flag if the register probe advances first, in which case it precedes Phase 4.
- **Phase 4 governance vs. Commitments 1 & 6**: the "publish pattern, not pillory" mechanism (system-truth transparency vs. individual dignity) needs real design before the first moderation action happens — not improvised live. Worth scoping as its own mini-spec before Phase 4 starts. **[PARTIALLY DISCHARGED 2026-07-17: the data-layer half is designed — capture schema v1.0 builds conflict rule 3 in structurally (reasoning split, templates, dignity test). Remaining for Phase 4: workflow/UI half (how moderation actions write entries in-flow, appeal surfaces) Research input compiled 2026-07-20: `research/moderation-engine-research.md` (kept in Claude Project Files for Now) — carries two new items for the mini-spec: victim-side workflow (not yet in schema or roadmap) and system-defect-first triage of moderation trends.]**

## How to Use This Document
 
- Phases are worked in order; do not advance to the next phase without confirmation, per working rules.
- Annotate phases here as work completes or scope shifts — this doc is the record of what actually happened, not just what was planned.
- If a phase requires reopening a Locked Decision in MVP_Spec.md, flag it explicitly rather than quietly proceeding.
- New Open Strategic Decisions or Deferred Features discovered mid-build get added to MVP_Spec.md, not buried only here.
